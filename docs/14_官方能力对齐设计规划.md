# 数字人 / 长视频质量提升：对齐 MiniMax 官方能力的完整设计

> 2026-11-02 现状盘点 + 分层规划。目标：从"能出片"推进到"官方演示级"。

## 一、先回答三个事实问题

### 1.1 负向提示词为什么不能用——是模型实现，不是部署配置

实测两个节点（12.252 双 4090D、107 双 3090），传 `negative_prompt` 报错完全一致：

```
MiniMaxH3Runner (t2av) does not support request fields: negative_prompt
```

根因两处，都在模型侧：

```python
# lightx2v/models/runners/minimax_h3/minimax_h3_runner.py:99
"t2av": COMMON_REQUEST_FIELDS | VIDEO_OUTPUT_FIELDS | {"prompt"},
# COMMON = {task, seed, save_result_path, return_result_tensor}
# VIDEO_OUTPUT = {size, num_frames}
# 没有并入 PROMPT_FIELDS（该集合里才有 negative_prompt）
```

```json
// minimax_h3_fp8_4step_tp2_4090.json
"enable_cfg": false
```

`enable_cfg: false` 意味着 4 步蒸馏推理**没有负向分支**，即使把字段放行也无处施加。
OpenAPI schema 里的 `negative_prompt` 是通用声明，不代表每个 runner 都实现。

**能不能修？** 能，但要打开 CFG——每一步要多跑一次前向，4 步变 8 步，耗时接近翻倍，
而且官方 Turbo LoRA 是**无 CFG 蒸馏**出来的，强行开 CFG 会和 LoRA 训练条件冲突。
**结论：不改模型，改用「正向描述 + 锚定图约束」达到同样目的。**

### 1.2 官方 skill 到底有几个

GitHub `MiniMax-AI/MiniMax-H3/skills/` 下共 **9 个**，每个都有 `SKILL.md` / `SKILL.cn.md` / `meta.yaml`：

| skill | 定位 | 和我们场景的关系 |
|---|---|---|
| `h3-prompt-writing` | 通用写法规范：五种模式、三段式字段、镜头语法、对白语法 | **全站底层，必须内置** |
| `minimalist-product-ad-generator` | Apple 风极简产品广告，10 步工作流 | **最贴合电商，重点吸纳** |
| `brand-promo-video-generator` | 品牌宣传片，需 LOGO/官网/素材核验 | 可做"品牌片"模式 |
| `3d-animation-short-generator` | 3D 动画短片，角色卡 + 场景卡 + 镜头表 | 可做"动画"风格选项 |
| `paper-collage-explainer-generator` | 纸拼贴讲解 | 内容型，非电商首选 |
| `papercraft-stop-motion-explainer` | 纸艺定格讲解 | 同上 |
| `handdrawn-live-video-generator` | 手绘实拍混合 | 同上 |
| `music-video-subtitle-generator` | 音乐视频 + 字幕卡点 | 可做"卡点混剪" |
| `co-op-game-intro-generator` | 多人游戏开场 | 场景较远 |

**你提到的 POV 不是独立 skill**，它是 `h3-prompt-writing` 运镜词表里的一个选项
（`POV` 与 Zoom/Push/Pan/Truck/Tilt/Pedestal/Arc/Tracking/Static/Shake/Roll 并列）。

### 1.3 部署能力边界（决定了能做到什么程度）

12.252 容器内：

```
/workspace/models/MiniMax-H3/transformer        ← 有，基础分支
/workspace/models/MiniMax-H3/transformer_ref    ← 没有
```

`get_supported_tasks()` 对基础分支返回 `t2av / i2av / l2av / fl2av / ref2av`，
但 **ref2av 需要 `transformer_ref` 权重**，当前缺失。所以：

| 能力 | 现状 | 输入上限 |
|---|---|---|
| t2av 纯文字 | 可用 | 1 段文字 |
| i2av 首帧 | 可用 | 1 张图 |
| fl2av 首尾帧 | 可用 | 2 张图 |
| **ref2av 多参考** | **不可用**，缺权重 | 官方支持 9 图 + 3 视频 + 3 音频 |

官方产品广告 skill 要"三张独立锚定照片"，我们**暂时只能给 2 张**。

## 二、为什么官方片子更"真"——差距不在参数，在工作流

把官方 `minimalist-product-ad-generator` 的 10 步拆开看，和我们现在的做法对比：

| 环节 | 官方做法 | 我们现在 | 差距性质 |
|---|---|---|---|
| 素材分析 | 提炼产品品类、主色、可展示结构 | 用户写一句商品描述 | **信息量差一个量级** |
| 视觉锚定 | **三张独立锚定照片**（主视觉 / 材质细节 / 结尾构图），生视频时**不传原商品图** | 无，直接文字生成 | **缺失整层** |
| 分镜 | 精确节拍表：时间段/镜头目的/视觉主导/运镜/款式状态/文案/文字颜色/转场/节奏 | LLM 自由发挥一段 JSON | 精度差一个量级 |
| 镜头控制 | 每节拍只允许一个主要动作，次级延迟 | 无约束 | 无 |
| 色彩保真 | 产品本体颜色硬约束，只允许改背景和光 | 无约束，模型自由发挥 | 无 |
| 声音 | H3 原生音频 + Apple 风配乐方向写入 prompt | 数字人整条 **N/A**（要被 TTS 覆盖） | 场景不同，合理 |
| 分辨率 | 768p（LoRA 训练分辨率） | 540P / 736×1280 | 参数未对齐 |

**核心结论：官方效果 ≈ 锚定图锁产品 + 节拍表锁节奏 + 768p + 原生音频。
我们缺的是前两项的方法论，不是模型能力。**

特别值得注意的一条：官方明确要求 **"生视频阶段不要把用户上传的原商品图传给视频模型"**，
原图只用于分析、生成锚定图。我们之前的"商品图直接当首帧"反而会让模型
把商品图的原背景、原光线一起带进来，看起来像"图生视频"而不是"实拍"。

## 三、分层实施方案

### L0 已完成（本轮）

- 三段式纯文本前缀（替代 `JSON.stringify`）
- 首镜头 `[Shot 1]` + 画幅描述（竖屏 9:16 构图）
- `Static Shot` 固定机位（数字人）
- 负面词改明确陈述句
- 数字人 `silentAudio: true`：跳过 LLM 分镜、声音 N/A
- 分段重试 5 次 + 指数退避
- `planSegmentFrames` 帧数整体分配（17n+5 对齐）

### L1 通用写法补齐（1–2 天，零风险）

目标：所有出片路径都符合 `h3-prompt-writing` 规范。

1. **描述改英文**。官方 Output Rules 明确 "Write rewrite sections in English;
   preserve dialogue, lyrics, and visible scene text in their original language"。
   现在的场景库、人物描述、商品描述都是中文，需要一层"中文意图 → 英文描述"的翻译，
   但对白和画面内文字保留中文。
2. **多镜头用时间戳**。`[Shot 2] At 00:03.500, the camera cuts to...`，
   替代现在"第 N 段"这种自然语言分段说明。
3. **运镜写成自然句**，不再堆"镜头：xxx"标签。
4. 建立 `promptSpec.js` 做统一校验：字段齐全、时长与帧数匹配、单镜头动作数 ≤ 1。

**收益**：画面指令更被模型接受，切镜更准。**成本**：需重写 `buildHumanScenePrompt`
和 `longVideoPlanningMessages` 的模板。

### L2 电商工作流（核心，3–5 天）

这是从"能出片"到"能商用"的分水岭。把官方 10 步压成我们产品的 4 步：

```
① 商品事实提取  上传商品图 → 视觉模型输出：品类/主色/材质/可展示结构
② 锚定图生成    生成 2 张（暂受 ref2av 缺失限制）：
                   A 主视觉/刁钻主视角   B 材质细节或结尾构图
                 用户可换、可重生成
③ 节拍表确认    时间段 / 画面主导 / 运镜 / 文案 / 转场 / 节奏意图
                 用户在页面上可改每一行
④ 逐段生成      每段都以锚定图为视觉锚：
                   第 1 段 i2av(锚定图 A)
                   第 N 段 fl2av(锚定图 A + 上一段末帧)
                 产品锁定 + 动作连续，同时解决"逐段漂移"和"接缝跳变"
```

关键设计：**第 N 段挂锚定图而不是只挂上一段末帧**。
现在是纯链式（末帧→首帧），误差逐段累积；加入锚定图后每次回到"正确产品"，
漂移不会累积。这是长视频保真的正解。

**成本估算**：每张锚定图约 10–15 秒（Qwen-Image），2 张 +30 秒；
但能省掉现在的失败重试（单段失败一次就是 2–4 分钟），整体可能反而更快。

### L3 部署能力补齐（需动服务器，按收益排序）

| 项 | 动作 | 收益 | 成本/风险 |
|---|---|---|---|
| **768p 默认** | `h3Size` 增加 `[1344,768]`，数字人/长视频切过去 | LoRA 训练分辨率，细节明显更实 | 需重测显存；124 帧实测 100 秒可跑 |
| **ref2av 权重** | 下载 `transformer_ref`（数十 GB）+ 重启服务 | 解锁 9 图参考，真正实现官方"三锚定图" | 磁盘 1.7T 够；重启约 2.5 分钟，需停机窗口 |
| **8 步 LoRA** | 换 `minimax_h3_fl2v_turbo_8step_v1.0_768p` | 质量更高、细节更好 | 耗时约翻倍（单段 5 秒从 100s → 200s） |
| **music-2.6 配乐** | 长视频/品牌片接独立配乐 + 卡点 | 声音不再是 H3 随机生成 | 需接新模型 |
| **原生音频保留** | 商品广告类保留 H3 音轨，不用 TTS | 官方片的"临场感"很大来自原生音效 | 与数字人 TTS 链路冲突，需分模式 |

## 四、怎么"吸纳"这些 skill——不是装上，是拆开用

三种吸纳方式，用途不同：

**A. 当规范用（推荐）**
把 `h3-prompt-writing` 的规则固化成代码里的 `promptSpec.js`，
不依赖 agent 读文件，所有请求自动合规。skill 更新时同步改常量即可。

**B. 当流程用（L2）**
`minimalist-product-ad-generator` 的 10 步是给人看的问询流程，
我们把它变成产品里的分步向导（商品图 → 锚定图 → 节拍表 → 生成），
用户看到的是 4 个页面，不是 10 条 agent 指令。

**C. 当风格模板用（可选）**
其余 7 个 skill 抽成"风格选项"：3D 动画、纸拼贴、手绘、纸艺定格、音乐卡点、游戏开场。
每个模板只保留它的**视觉风格锁 + 镜头语言**（例如 3D 动画的"皮克斯感 C4D+Octane 质感、
2.5–3 头身 Q 版比例、SSS 皮肤"），流程复用 L2 那一套。

**关于"什么类型触发什么 skill"**：对，官方就是 `meta.yaml` 里的 `trigger-words` 做意图路由。
我们的产品不需要 agent 语义路由——用户在页面上选"做商品广告 / 做数字人口播 / 做动画短片"
就是显式触发，比关键词匹配更可靠。

## 五、建议的执行顺序

| 阶段 | 内容 | 预期效果 |
|---|---|---|
| 第 1 步 | L2 锚定图 + 每段挂锚定图 | **解决逐段漂移，商品保真**（收益最大） |
| 第 2 步 | L1 英文 prompt + 时间戳切镜 | 画面指令更准，切镜更自然 |
| 第 3 步 | L3 768p 默认 | 细节清晰度上一个台阶 |
| 第 4 步 | L2 节拍表交互 | 用户可控节奏，接近官方工作流 |
| 第 5 步 | L3 ref2av 权重 | 解锁真三锚定图 |
| 第 6 步 | L3 8 步 LoRA（可选开关"高质量模式"） | 极限质量 |

第 1 步就能看到明显差别，且不需要动服务器。
