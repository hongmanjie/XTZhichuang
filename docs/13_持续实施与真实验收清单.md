## 2026-10-31 下午：数字人配音质量修复

- 起因：用户反馈数字人成片声音僵硬、不像 TTS。排查发现旧音色 `ym_1_6cae...` 的参考音频约 5.2 秒中有 3.6 秒是静音，真正说话只有约 1.6 秒，且素材本身是合成音再克隆。同一段 50 字文案，旧音色合成 12.26 秒并在中间留下 1.49 秒空洞；系统内置音色为 10.90 秒、停顿正常。
- TTS 服务本身会在首尾各留 0.5–1.5 秒静音。文案“欢迎光临。”5 个字合成 3.11 秒，其中人声约 0.8 秒；旧链路再用 apad 把音频铺满 H3 最短的 124 帧（5.17 秒）画面，成片里大段是静音。
- 改动：新增 `server/src/services/voicePresets.js`，把 8 个已注册发音人以负数 id 作为内置音色提供；`synthesizeSpeech` 支持内置音色并在合成后裁剪首尾静音（保留 0.08/0.12 秒气口，句中停顿不动）；`humanVideo` 改为按配音长度裁画面，只在尾部留 0.35 秒；音色列表、配音、数字人三处校验同步放开内置音色，内置音色不可删除。
- 真实结果：任务 25，52 字文案，内置音色“热心女孩”，配音 11.20 秒，成片 11.58 秒、544×960、24fps、有音轨，FunASR 回读与文案完全一致。静音占比由旧成片约 44% 降到约 15%，最长停顿 0.48 秒，片首无静音。
- 未解决：H3 会自行在画面里生成文字，抽帧 OCR 判为 `text_detected` 后暂停叠加字幕，本次成片没有字幕；背景书架、桌面纸张上的印刷字也可能触发该判断，需要区分画面主体文字和背景文字。

## 2026-10-31 下午：数字人字幕链路重构

- 问题：旧流程检测到画面有文字就整段重生成一次（`maxQualityRetries: 1`），仍不行就整条不加字幕。实测那条 15 秒片里是桌面商品标签被当成字幕，导致成片一条字幕都没有；重生成还要多花 45–75 秒。
- 改动一：取消“检测到文字就重生成”，`generateLongVideo` 不再传 `validateSegment`/`maxQualityRetries`，省掉每段一次抽帧 OCR 和潜在整段重生成。
- 改动二：字幕不再被跳过。只要用户勾了字幕就一定烧录，检测结果不再作为开关。
- 改动三：字幕时间改成 ASR 对齐。`humanSpeechCheck` 把 FunASR 的每句起止一并存下来，新增 `subtitleAlign.timedSubtitleSegments` 按字符位置映射到真实停顿；识别不可用时退回按字数估算。实测同一段 50 字文案得到 6 行字幕，时间落在实际停顿上。
- 改动四：新增 `subtitleRepair.js` 与 `tools/vsr_service/server.py`，为“底部字幕带修复”预留接口：调用同机 VSR 容器只处理底部 18% 画面，返回清理后的视频；`SUBTITLE_REPAIR_BASE_URL` 留空则整步跳过，不阻断出片。
- 真实结果：任务 29，配音 9.88 秒，成片 544×960、24fps，字幕 `timing: asr_aligned`、共 6 段，抽帧确认只有一行字幕、无双行、无模型自带文字。总耗时约 264 秒，比任务 25 的 298 秒略快。
- 未完成：VSR 镜像（`eritpchy/video-subtitle-remover:1.4.0-cuda11.8`，约十几 G）从内网镜像源拉了 20 多分钟仍未完成，因此“字幕带修复”这一步只做了代码与配置，没有真实验收。镜像就位后需要启动容器、把 `SUBTITLE_REPAIR_BASE_URL` 指向它，再用带文字的画面复测。

## 2026-10-31 晚：数字人 200 字和商品图真实验收

- 长文案：当前产品上限是 200 个 JavaScript 字符单位（含标点和空格），201 字请求会被拒绝。这是系统限额，不是已证明的模型物理极限。原 IndexTTS 对 200 字单次输入出现严重遗漏；现按标点拆成每段最多 45 字配音并逐段回读，再根据实际音频长度调度视频。配音与文案严重不一致时在 H3 前停止，明确失败后可重试；未确定是否已提交的请求不会自动重复。
- 540P 真实任务 36：200 字，人物与商品图两张真实上传图；5 段 TTS、5 段 H3、5 段 LatentSync，出片 42.33 秒、544×960、24 fps 且有音轨。语音回读相似度 0.972，逐字时间映射相似度 0.989，28 行字幕。一次任务耗时约 20 分 48 秒；样片可见人物面部和衣服细节随分段缓慢漂移，商品字样和品牌无法承诺像素级保真。使用的是内置测试音色，不等于用户音色的主观质量已验收。
- 商品图：用户图片经本地透明化或使用原有透明通道，与人物画面合成实际首帧传入 H3；未选人物图时先文生人物背景。智能体依照分段文案规划自然展示动作。真实任务 35 的马克杯在画面中被拿起展示；这不能证明任何复杂商品和标签都能保真。
- 字幕：新增 Paraformer 原版 CPU 逐字时间服务，只在内网用密钥访问；不改网关。无法可靠对齐时回退估算并提示。按中文词边界和数字单位分行；任务 39 基于真实 200 字音频重新制作 28 行字幕，例如“三百五十毫升”和“喜欢”不再被拆开。任务 39 是对旧无字幕视频的独立补字幕，不是任务 36 的替换版。该旧样片杯体出现模型自行生成的蓝色字样，表明保留商品原有标签与清除虚构标签仍有冲突。
- VSR：实际使用官方镜像内 `backend/main.py` 的 `-i/-o/-c/--inpaint-mode sttn-det` 参数，HTTP 上下传是项目自己的封装。真实黄色乱码样片识别动态条带并修复，约 26.5 秒返回；复检为无可见叠加字。抽帧无字不动画面，不确定时暂停新字幕。检查和修复不能保证发现每一帧的字或绝不损坏附近像素。
- 720P：任务 37 在约 8 秒单段时实测 GPU0 显存不足，任务失败并退款。任务 38 用单商品图、自动人物、124 帧生成成功，输出 736×1280、4.21 秒，配音、口型、字幕均完成。为降低风险，720P 为每段最多 124 帧，预留点数按每 18 字一段估算，按实际段数结算并退回剩余部分。任务 40 的两段 720P 画面和口型已生成，由于一次文字检查临时失败而暂停字幕。复查无叠加字后，任务 41 为其单独补加对齐字幕。现对单次抽帧或识别失败加一次重试；两次均失败仍停止添加字幕。任务 42 的画面及口型生成成功，但字幕检查再次失败，不能把此次算作全流程成功。随后任务 43 使用 34 字、人物图和商品图实测两段 720P H3 及口型，自动字幕开启并成功对齐 5 行，成片 736×1280、7.96 秒、有音轨，约耗时 6 分 27 秒。前两次检查不可用的具体原因仍未确认；已添加不记录用户内容的故障阶段诊断，仍需多次和并发测试。
- 稳定性与存储：隔离应用使用 Redis 共享 H3 锁，只对指向同一 Redis 和同一 key 的进程生效；其他项目和直连请求不受约束。字幕时间服务占用 2 CPU、空闲约 3.5 GiB 内存，已限制最多 6 GiB。上传图像在测试应用 uploads Docker 卷和 `materials` 表；选图弹窗支持继续加载、有权限的删除，已修复删除后搜索索引异步重现的竞态。
- 页面验收：Chrome 连接返回 `Debugger unattached` 后改用隔离的无头 Firefox 验收。实测过程发现测试站使用根路径构建导致 `/xtzc/` 直达数字人页 404，已重新以 `/xtzc/` 构建。该浏览器已实际验证 200 字限额、720P 预留点数、页面上传、历史选图、弹窗确认删除、草稿保留及已选图片自动清除。实测历史任务的缺字幕提示可见，最新成片能在页面加载。
- 上线前仍需：正式对公网部署前，VSR 服务当前无认证并绑定所有网卡，需限制访问或增加认证；还需备份、多用户压力及长片商品和人物一致性测试。

## 2026-10-31 深夜：数字人检查链简化 + VSR 区域验证

- 验证了 VSR 的区域参数：同一段画面中部有字的测试片，传 `bandTop=0`（全画面）能把中间的字擦掉，传 `bandTop=0.86`（只修底部）则完全不动。说明 VSR 本身不分区域，限制来自我们传的 `-c ymin ymax xmin xmax`。
- 数字人流程改成一次带内粗检（每段 3 张图）：
  - 有字 → VSR 按检测到的上下边界修；
  - 没字 → 直接加字幕；
  - 查不出来 → 按“可能有字”处理，照样修、照样加字幕（fail-open）。
- 去掉了修复后的复检和口型后的二次检查，OCR 调用从每任务约 60 次降到约 6 次。
- 字幕不再由检测结果决定加不加，只由用户勾选决定；`textCheck` 退化为信息字段。

## 2026-11-02：H3 官方规范对齐、负面约束根因、分段重试与帧数规划

### 一、负面提示为什么不能用：不是网关，是模型 runner

直连 192.168.12.252:9001（主节点，双 4090D）与 192.168.86.107:9001（备用，双 3090）都实测过，
传 `negative_prompt` 都会失败，报错完全一致：

```
MiniMaxH3Runner (t2av) does not support request fields: negative_prompt
```

根因在 `lightx2v/models/runners/minimax_h3/minimax_h3_runner.py:99`：

```python
supported_request_fields_by_task = {
    "t2av": COMMON_REQUEST_FIELDS | VIDEO_OUTPUT_FIELDS | {"prompt"},
    ...
}
# COMMON_REQUEST_FIELDS = {return_result_tensor, save_result_path, seed, task}
# VIDEO_OUTPUT_FIELDS  = {size, num_frames}
# 未包含 PROMPT_FIELDS（含 negative_prompt）
```

而实际配置 `minimax_h3_fp8_4step_tp2_4090.json` 里 `enable_cfg: false`——
关闭 classifier-free guidance 后推理没有负向分支，负面提示无处可用。
通用 OpenAPI schema 里虽然列了 `negative_prompt`，但那是所有模型共用的声明，
H3 这个 runner 明确没有实现。

**结论：网关没问题、部署没问题，是模型侧不支持。只能把约束写进正向提示词。**

### 二、官方文档查到的真实约束

来源：`/workspace/LightX2V/scripts/minimax_h3/README_zh.md`（12.252 容器内），
以及官方仓库的 `skills/h3-prompt-writing/references/base-en.txt`。

- **尺寸**：`size` 为 `[高度, 宽度]`，宽高必须是 **32 的倍数**。
- **帧数**：向上对齐到 `17n+5`，对齐后须在 **124–362** 之间（如 125 → 141）。
  输出固定 **24 FPS + 32 kHz 立体声**。系统此前硬编码的 `[124..226]` 是自己设的上限，不是模型上限。
- **提示词结构**：三段式 **纯文本前缀**，不是 JSON。
  `integrated_multimodal_description` / `overall_soundscape` / `non_diegetic_music`。
  官方 `post_t2av.py` 示例就是这个写法；系统此前用 `JSON.stringify` 包成大括号字符串，偏离官方。
- **镜头语法**：`[Shot 1]` 不加时间戳，后续镜头 `[Shot 2] At 00:03.500, the camera cuts to...`；
  运镜写成自然句子 `The camera pushes in with small amplitude at slow speed`，
  固定机位用 `Static Shot`。
- **声音字段**：`overall_soundscape` 只写环境音/foley，不要重复对白；
  `non_diegetic_music` 写乐器、速度、节奏，**不要抽象情绪词**；没有就写 `N/A`。
- **画面内文字**：官方做法是**明确写出来**（`A red neon sign reading "营业中"`），
  而不是列举“不要字幕、不要水印”——列举这些词反而会把概念带进注意力。
- **官方 skill**：`npx skills add https://github.com/MiniMax-AI/MiniMax-H3 --skill h3-prompt-writing`，
  仓库共 9 个 skill（1 个写法规范 + 8 个风格生成器）。
- **官方 LoRA**：`minimax_h3_fl2v_turbo_4step_v1.1_768p_bf16`（12.252 在用），
  768p 是训练分辨率；4 步推理配 `video_flow_shift 6.0`、`audio_flow_shift 3.0`、
  `h3_step_update training_euler`、`alpha 128`。另有 8 步版本可选（质量更高、耗时翻倍）。

### 三、768p 实测

`size=[1344,768]`（768 宽 1344 高），124 帧，直连 12.252：**100 秒跑通**（比 736×1280 的 120 秒快）。
但抽帧发现**横构图被塞进竖屏**：人物和商品并排、两侧被裁。
原因是提示词只给了尺寸、没写画幅，模型按默认横构图理解。
这直接促成了本次“画幅必须写进提示词”的改动。

### 四、代码改动（8+4+3 处）

1. `buildMiniMaxPrompt` 改成官方三段式纯文本，新增 `size` 参数自动补画幅描述，
   首镜头补 `[Shot 1]`（调用方已写则不重复）。
2. `DEFAULT_VIDEO_NEGATIVE` 从 12 个中文负面词改为一句明确陈述：
   `No on-screen text, captions, subtitles or watermarks appear in any frame`，
   拼接方式从“避免出现：xxx”改为直接陈述。
3. 数字人提示词加 `Static Shot，机位与焦段保持不动`，抑制人脸漂移、利于口型对齐。
4. 数字人调用加 `silentAudio: true`：**跳过 LLM 分镜**（它会把人物和商品描述改写丢细节），
   音景/配乐传 `N/A`（反正音频会被 TTS 完全覆盖）。
5. 分段重试 `H3_SEGMENT_ATTEMPTS` 默认 **3 → 5**，退避改为指数 **5/10/20/40 秒**。
6. 新增 `planSegmentFrames(durations, resolution)`：按“剩余目标均分”分配每段帧数，
   替代原先逐段向上取整，减少累积误差。实测：
   - 15s/720P → 124×3 = 15.50s（误差 +0.50）
   - 15s/540P → 192+175 = 15.29s（+0.29）
   - 30s/720P → 158+141×4 = 30.08s（+0.08）
   - 60s/540P → 192×3+175×5 = 60.46s（+0.46）
