## 二、🔴 P0 阻断级（建议优先修复）

### P0-1【实测】ES 混合检索被 kNN 污染，搜索功能实质失效

| 项 | 内容 |
|----|------|
| **位置** | `server/src/services/esService.js:216, 238-255` + `server/src/routes/material.js:92` |
| **现象** | 搜索任意关键词（含完全无意义的乱码）都返回恰好 `pageSize` 条结果；无关结果被大量灌入 |
| **证据** | 搜索「zzzzqqqq」→ 返回 5 条「精品咖啡豆特写/冷萃咖啡冲泡」；直连 ES 纯 BM25 查同一词返回 0 条。搜索「口红」时纯 BM25 正确返回 6 条且相关性排序正确，走应用接口则被稀释 |
| **根因** | `knn` 被放入 `bool.should` 且 `minimum_should_match:1`；而 kNN 语义天然"永远返回最近的 k 条"，与查询词相关性无关。`k = Math.min(60, from+size)` 恰好等于一页大小，于是每次都填满 |
| **叠加问题** | `material.js:92` 传 `sort:[{created_at:'desc'}]` → ES 忽略相关性评分（前端拿到 `_score:null`），且 `esService.js:265` 的 `!sort` 条件使 Rerank 精排被完全旁路 |
| **影响** | 资产库搜索、爆款搜索、脚本搜索全部失效。这是 README 单独设章节宣传的核心能力 |

**修复方向**：
1. kNN 与 BM25 分离为两路召回，在应用层用 RRF（Reciprocal Rank Fusion）融合，而非塞进同一个 `should`
2. kNN 结果按 cosine 相似度设阈值过滤，丢弃低分无关项
3. `k` 改为固定超召回（如 `min(50, ...)`），经 Rerank 后再截断到 `size`
4. 让 Rerank 与 sort 可共存：先相关性召回 + Rerank，再在结果内排序
5. 回归验证标准：无意义关键词返回 0 条；「口红」返回 6 条且相关项排前

### P0-2【实测】前端三处创作页文件未真实上传，把 blob URL 当文件传给后端

| 项 | 内容 |
|----|------|
| **位置** | `VideoGoldTime.tsx:19-24,40` · `HdVideo.tsx:19-23,29` · `EraseTool.tsx:58-67,74` |
| **现象** | 用户选择本地文件后，前端只用 `URL.createObjectURL()` 生成 `blob:http://localhost/xxx` 做预览，随后把这个 blob URL 直接提交给后端 |
| **后果** | ① 后端存进 DB 的是本地临时 blob 地址，服务重启即失效；② AI 引擎拿到 blob URL 无法下载处理；③ `HdVideo` 的"修复结果"直接回显同一个 blob URL，等于什么都没做；④ `EraseTool` 把数十 MB 的 base64 整体写进 SQLite |
| **对照正确写法** | `AIProductStudio.tsx:22-39` —— 先 `createObjectURL` 预览，再 `api.uploadMaterial(fd)` 真实上传，用返回的 `material.url` 提交。**三个页面应照此改造** |

**附带**：`EraseTool.tsx:74-86` 的消除流程完全忽略后端返回的 `resultUrl`，2.5 秒后直接 `setResult(imageUrl)` 把原图当结果显示；"保存到资产库"按钮不调任何接口——**整个消除笔功能是前端假装完成的**。

## 三、🟠 P1 严重级

### P1-1【实测】上传文件目录无鉴权，任意人可下载全部 AI 产物

```
不带任何 token 请求：
GET /uploads/ai_1793031284775_1138.mp4  →  HTTP 200，1,365,368 字节 ✅ 直接下载成功
```

- **位置**：`index.js:25` `app.use('/uploads', express.static(UPLOAD_DIR))`、`material.js:38` `router.use('/files', express.static(...))`
- **后果**：所有用户上传的素材图片/视频、AI 生成的商拍图与成片，**任何人无需登录即可通过 URL 直接下载**
- **说明**：目录列举返回 404（仅因未开启 autoindex），但知道文件名即可直接取到
- **建议**：静态挂载前加 `authRequired`；或改用签名 URL / 带时效的 token 访问

### P1-2【实测】CORS 允许任意源

- **位置**：`index.js:20` `app.use(cors())`（无 origin 配置）
- **实测**：请求头带 `Origin: http://evil.example.com`，响应 `Access-Control-Allow-Origin: *`
- **后果**：任意第三方站点可跨域调用全部 225 个 API
- **建议**：`cors({ origin: 白名单, credentials: true })`

### P1-3【实测】越权（IDOR）：大量写操作未校验 `owner_id`

用普通账号请求不存在的 ID，`code=0` 正常返回——说明接口**根本没做归属校验**，换成真实 ID 即可越权操作他人数据：

| 接口 | 位置 | 风险 |
|------|------|------|
| `POST /api/material/delete` | `material.js:135` | 删除他人素材 |
| `POST /api/material/update` | `material.js:123` | 篡改他人素材 |
| `GET /api/material/detail` | `material.js:115` | 读取他人素材 |
| `POST /api/script/delete`、`/api/work/delete`、`/api/folder/delete` | `material.js:200/220/54` | 删除他人脚本/作品/文件夹 |
| `POST /api/task/delete`、`/task/cancel`、`/task/retry`、`GET /task/detail` | `create.js:105-124` | 删除/取消/读取他人 AI 任务 |
| 精彩片段 clip 系列 5 个接口 | `creative.js:51-76` | 操作他人片段 |
| `scriptDetail.js` 全 8 个接口 | `scriptDetail.js` | 清空他人脚本分镜（`:83` 直接 `DELETE FROM script_subitems WHERE script_id=?`） |
| `ads.js` 全 15 个接口 | `ads.js` | 广告账户/广告组/投放数据跨用户 |
| `GET /api/member/order/order/status` | `biz.js:37` | 遍历订单号探测他人订单 |
| `GET /api/my/project/team/item?type=tdxm` | `biz.js:92` | 返回全库项目/品牌 |

- **当前影响**：单租户演示环境，暂无实际危害
- **建议**：所有带 `owner_id` 的表，查询/更新/删除统一追加 `AND owner_id = ?`；或抽一个 `scopeOwner()` 中间件

### P1-4【审查】JWT 密钥硬编码兜底值

- **位置**：`middleware/auth.js:4` → `process.env.JWT_SECRET || 'yimetai-clone-secret-key-2026'`
- **后果**：`.env` 缺失时，任何人可用这个**已写死在源码里**的常量伪造任意用户（含 `role_id=1` 超管）的 JWT，直接接管全站
- **建议**：密钥缺失则应启动失败，而非静默降级

### P1-5【审查】`.env` 明文密钥与仓库共存

`server/.env` 内含 4 个真实密钥：`WANJIE_API_KEY`（JWT 型）、`QWEN_API_KEY`、`SILICONFLOW_API_KEY`、`MODELGATE_API_KEY`。**本项目未初始化 git**，暂无外泄渠道，但一旦纳入版本控制即泄露。

**建议**：确认 `.gitignore` 包含 `.env`；提供 `.env.example` 模板；已泄露的密钥建议轮换。

### P1-6【审查】模拟支付无签名校验

- **位置**：`charge.js:27-36` `POST /api/charge/pay`
- **实测**：伪造订单号被拒（因订单不存在）；但**任何合法订单号可被任意重放**，客户端自报 `orderNo` 即加点数
- **风险**：接口形态与真实支付一致，接入真实渠道时极易被原样保留
- **建议**：接入真实回调签名校验，或至少校验订单归属当前用户

### P1-7【实测】种子数据归属混乱，导致列表与统计自相矛盾

数据库 `owner_id` 实际分布：

| 表 | 分布 |
|----|------|
| `materials`（32 条） | owner 2:5 · 3:6 · 4:2 · 5:6 · 6:6 · 7:7 —— **超管(id=1) 一条都没有** |
| `scripts`（8 条） | owner 3:1 · 4:2 · 5:1 · 6:2 · 7:2 —— **超管一条都没有** |
| `works`（8 条） | owner 1:8 |

**用户可见的矛盾**：

```
资产库列表 /api/material/list     → total = 32   （无 owner 过滤）
工作台统计 /workbench/data/init/new → {"material":0, "script":0, "work":8}  （按 owner 过滤）
看板核心指标 /data/board/config/core → 我的作品 8 / 我的脚本 0 / 素材资产 0
```

即：**资产库显示 32 个素材，Dashboard 却说"素材资产 0 个"**。

- **根因**：① 种子数据把素材/脚本分给了团队成员；② 列表接口不过滤 owner，统计接口过滤 owner
- **建议**：种子数据统一归属到演示主账号；列表与统计的 owner 过滤口径保持一致

### P1-8【实测】登出后 Token 仍完全有效

- **位置**：`auth.js:62` `POST /api/logout` 为空实现
- **实测**：登出后携带原 Token 请求 `/api/user/info` → HTTP 200，正常使用
- **后果**：JWT 有效期 7 天且无黑名单，登出形同虚设；共用电脑上无法真正退出
- **建议**：维护 token 黑名单/版本号，或缩短有效期 + 前端主动丢弃

## 八、风险提示

| 风险 | 说明 |
|------|------|
| **密钥安全** | `server/.env` 含 4 个真实 API 密钥，且项目未初始化 git。若后续 `git init` 并推送，密钥将外泄。建议立即确认 `.gitignore`，并考虑轮换已出现在本地文件中的密钥 |
| **多用户就绪度** | 当前代码按"单租户演示"假设编写，租户隔离缺失是**系统性的**（非个别接口遗漏）。若计划支持真实多用户，需要一轮完整的归属校验改造 |
| **部署形态不一致** | README 描述 `docker compose up -d` 启动三容器，实际只有 ES 容器在跑，应用由本地 Node 进程提供。生产上线前需验证完整容器化链路 |
| **上传目录路径解析** | `index.js`/`material.js` 用 `process.cwd()` 解析 `UPLOAD_DIR`，`aiProviders.js` 用 `path.resolve(__dirname,...)`。从仓库根目录启动会导致上传成功但 404 |
